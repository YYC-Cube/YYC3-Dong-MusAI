## 二、深度维度分析

### 2.1 架构合理性

**现状**：采用“前端 SPA + Express API + 数据库”的三层结构，目录按业务域拆分，方向正确。后端有 `routes/models` 分层意识。

**问题**：

1. 数据访问层三分叉：MongoDB（`server.js`）、SQLite（`server-sqlite.js`）、Mock（`server-mock.js`）同时存在，路由实现重复（`musicRoutes.js` 与 `musicRoutes-mock.js`）。**2026-11-07 已确认目标唯一事实源为 PostgreSQL 15（`yyc3_music`，本地 5433；NAS Docker `yyc3-music`）**，但 PG 适配层尚未落地。
2. 同一接口在不同实现下语义不一致：Mongo 版 `GET /api/music/releases` 在空库时会**自动写入 3 条示例数据**（[musicRoutes.js](../../api_service/src/routes/musicRoutes.js)），SQLite 版不会；响应字段结构亦有差异。
3. `server.js` 同时存在 `startServer()` 内 `app.listen` 与文件末尾再次 `app.listen`（[server.js](../../api_service/src/server.js)），构成重复监听。
4. 前端 `HomePage.jsx` 内重新实现了 `EnhancedMusicPlayer`、`LatestReleases`、`FanWall`，与 `components/` 下同名组件重复，形成“双实现”。

**影响**：新增功能时无法确定“唯一事实源”，联调与测试成本翻倍；部署时可能启动两个监听导致 `EADDRINUSE`；重构风险高。

### 2.2 代码质量

**现状**：JavaScript（非 TypeScript），函数式组件 + Hooks，命名基本符合 camelCase/PascalCase。

**问题**：

| 指标 | 实测值 | 评价 |
| ---- | ------ | ---- |
| 最大单文件 | `HomePage.jsx` 1,097 行 | 严重超限（建议 ≤ 300 行） |
| 重复实现 | 3 组组件双实现，约 2,000 行重复 | 高 |
| `console.log` | 30 处 | 中 |
| 内联样式 | 20 处 | 低 |
| TODO/FIXME | 0 处 | 表面良好，但存在“伪完成”注释 |
| 异常处理 | 路由层均 `try/catch`，但仅返回 500，无错误码体系 | 中 |
| 注释完备度 | 业务注释少，Swagger 注释较完整 | 中 |
| 类型安全 | 无 TypeScript、无 PropTypes | 低 |

**影响**：维护者理解成本高；重复代码导致“修一处漏一处”；无类型约束使接口字段变更极易引发运行时错误。

### 2.3 技术债务

| 债务项 | 位置 | 等级 | 说明 |
| ------ | ---- | ---- | ---- |
| 重复监听 | `api_service/src/server.js` | P0 | 启动即冲突风险 |
|  compose 引用不存在服务 | `docker-compose.yml` | P0 | `./ai_services/lyrics_generator` 不存在 |
| 资源路径全量失效 | 前端 `/assets/**` | P1（本次已修复） | 真实资产在 `public/D-*` |
| 无 Git | 仓库根 | P0 | 不可追溯 |
| 三套数据实现 | `api_service/src` | P1 | 目标 PG15 已确认，代码未迁移 |
| 种子脚本与表结构不一致 | `content_db/seed_data/initial_artist_data.sql` | P2 | 使用 `artist_id`，表为 `artistId`；`exclusive_content` 表不存在 |
| 过时依赖 | Mongoose 6 / Cloudinary 1 / CRA 5 | P2 | 已停止主流维护 |
| 空壳模块 | admin/mobile/marketing | P2 | 承诺与交付不符 |
| 文档冲突 | `docs/*.md` | P2 | README 称 MongoDB，README_DEV 称 SQLite |
| 端口不合规 | 3000/4000 | P3 | YYC³ 要求自 3030 起 |

**影响**：技术债集中在“启动、部署、数据一致性”三处，属于会直接阻断交付的类型。

### 2.4 性能风险

**现状**：无压测数据、无 APM、无日志聚合。可静态识别的风险如下。

| 风险点 | 说明 | 影响 |
| ------ | ---- | ---- |
| 列表无强制上限 | SQLite 版 `limit` 直接来自 query，未做 `1..100` 约束 | 超大 `limit` 可拖垮进程 |
| 全表排序 | `/api/music/featured` 使用 `json_extract(stats,'$.plays')` 排序 | 数据量增大后无法走索引 |
| 粉丝墙固定 20 条 | 尚可，但无分页游标 | 后续扩展受限 |
| 前端粒子动画 | `DynamicBackground` + 64 根可视化柱每 100ms 更新 | 低端设备 CPU/GPU 压力 |
| 音频资源 | 11 首 MP3 共约 55 MB，未做码率分级/懒加载 | 首屏与移动流量成本高 |
| 无缓存 | Redis 声明但未接入 | 重复查询 |
| 无 gzip/压缩 | Express 未启用 `compression` | 传输体积偏大 |

**影响**：当前演示规模可接受；一旦真实粉丝量级上来，列表接口与静态资源将成为首批瓶颈。

### 2.5 安全风险

| 风险 | 位置 | 等级 | 说明 |
| ---- | ---- | ---- | ---- |
| 硬编码密钥 | `api_service/.env` | P1 | `JWT_SECRET`、Mongo URI 明文 |
| 写接口无鉴权 | `POST /api/music/:id/play` | P1 | 任意来源可刷播放量 |
| 认证依赖空转 | `bcryptjs`、`jsonwebtoken` 已安装但无登录/校验中间件 | P1 | 安全能力“有壳无实” |
| 输入校验缺失 | `limit/page/type` | P1 | `express-validator` 已装未用 |
| 错误信息泄露 | 错误处理中间件在 development 下回传 `error.message` | P2 | 生产需关闭 |
| CORS 白名单 | `FRONTEND_URL` 单值 | P2 | 多端部署需扩展 |
| 依赖漏洞 | `npm audit` 实测 43 项（3 critical / 17 high） | P1 | 含 `fast-xml-parser`、`proxy-addr`、`tar` 及直接依赖 express/mongoose/sqlite3 |
| 媒体版权 | `public/D-Music`、`D-cover`、`D-poster` | P1 | 需明确授权范围，代码许可证不覆盖媒体 |

**影响**：当前最现实的风险是“播放量可被任意刷写”和“密钥随目录扩散”；上线前必须整改。

### 2.6 可维护性

| 维度 | 评价 | 说明 |
| ---- | ---- | ---- |
| 部署复杂度 | 高 |  compose 必失败；前端 Docker 用 CRA dev server |

### 3.3 结论

- **静态层**：全部通过。
- **运行层**：SQLite API 已真实启动并完成冒烟，5 个端点返回 200；写接口可用。
- **测试层**：后端 2 个测试套件、7 个用例全部通过（依赖本机 MongoDB）。
- **阻断项**：`/api/content/*` 在 SQLite 入口下全部 404，与 Mongo 入口契约不一致。
- **环境缺陷**：`.env` 的 `MONGODB_URI` 指向 Docker 主机名 `db`，本地 Mongo 模式启动后查询在 10s 后超时。
- **校验缺陷**：`limit/page` 无边界校验，非法输入触发 500，超大输入不设上限。
- **依赖风险**：`npm audit` 检出 43 项漏洞，其中 3 项 critical（`fast-xml-parser`、`proxy-addr`、`tar`），直接依赖 `express`、`mongoose`、`sqlite3`、`cloudinary`、`validator` 均有 high 级告警。
- **未覆盖**：前端构建与浏览器 E2E、性能。
